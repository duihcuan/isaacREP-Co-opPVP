## 0. 这套流程解决什么问题

"正规的企业级测试"不是更多人工点击，而是三条硬标准：

1. **可复现**：任何人按同样的步骤、同样的环境，能得到同样的结果。
2. **有证据**：每个结论都能指向日志片段、截图、录像或自动化输出，而不是"我试过了没问题"。
3. **可回归**：每次改代码，同一套验证能重跑，并且能立刻看出哪个能力退化了。

游戏模组测试与后端测试最大的差别只有一个：**被测系统是图形程序，没有现成的测试运行器可以驱动它**。因此本流程的核心手法是——把"判断"交给脚本，把"操作"留给人；凡是不需要眼睛的验证，一律自动化。

## 1. 角色与职责

单人项目也要在文档里写清角色，否则你会不断在"写代码的人"和"验代码的人"之间混淆标准。

| 角色 | 单人项目中的做法 |
|---|---|
| 测试负责人 | 由你兼任。负责测试计划、准出标准、最终签字 |
| 测试执行人 | 由你兼任。**执行时只按用例走，不临时发挥** |
| 开发 | 由你兼任。**修缺陷时不许顺手改需求** |
| 评审人 | 缺失。用书面模板代替口头评审：缺陷单、测试报告必须写全字段 |

关键纪律：**执行测试时，不修改代码；修改代码时，不夹带测试结论。** 这两件事混在一起，是个人项目最常出现的"测试失真"。

## 4. 主流程总览

```
P0 准备与计划  →  P1 需求分析  →  P2 用例设计  →  P3 环境准备
      →  P4 冒烟测试  →  P5 功能测试  →  P6 探索性测试
      →  P7 缺陷管理  →  P8 回归测试  →  P9 兼容性与稳定性  →  P10 出报告与准出
```

每个阶段都按 **目标 → 输入 → 步骤 → 工具 → 产出 → 完成标准** 六段执行。P7 缺陷管理是横跨全程的，不是某个阶段。

## 5. 阶段详解

### P0 准备与计划

**目标**：把"测什么、不测什么、什么情况算通过"写死，避免边测边改标准。

**输入**：规格文件第 8 节验收标准；计划文件的 M0–M4 里程碑。

**步骤**

1. 划定本轮范围。M1 本轮只测：模式启用、房间锁定、玩家互伤、胜负结算、非 PVP 隔离。
2. 明确不测范围，并写明原因：M2 血量池、M3 道具争抢、M4 平衡与设置尚未实现。
3. 定义准出标准（见第 7 节），必须是可量化的数字。
4. 评估资源与风险：轮次时长、手柄可用性、其余 30 个 mod 的干扰风险。

**工具**：VS Code 编写 Markdown；需要对外分享时上传语雀或飞书。

**产出**：`docs/testing/test-plan.md`

**完成标准**：不看代码，只读测试计划，就能说出本轮测什么、不测什么、通过线在哪。

---

### P1 需求分析（提取可测项）

**目标**：把规格里每一句需求，翻译成能用"是/否"回答的判定条件。

**输入**：规格文件第 8 节验收标准。

**步骤**

1. 逐条摘出验收标准，编号为 `REQ-M1-01`、`REQ-M1-02`……
2. 对每条问一句："用什么动作、观察什么现象，就能判定它成立？"
3. **改写不可判定的表述。** 例："房间锁定"不可判定，改成"在竞技场房间内执行 12 种离开尝试，全部失败且未发生换房"。
4. 建立需求跟踪矩阵：REQ ↔ 测试用例 ↔ 缺陷。

**工具**：Markdown 表格；规模化后迁移到禅道的需求与用例模块。

**产出**：`docs/testing/traceability.md`（需求跟踪矩阵）

**完成标准**：规格里每条验收标准至少对应一条 REQ，且每条 REQ 都能用一句是/否的问题回答。

---

### P2 用例设计

**目标**：把可测项变成"别人照着做也能得到同样结果"的步骤。

**方法**（你从后端测试已经掌握，可直接迁移）：等价类划分、边界值分析、状态迁移法、场景法、错误推测法。

**本项目的具体应用**

| 方法 | 在本项目怎么用 |
|---|---|
| 等价类划分 | 攻击类型 {眼泪, 激光, 菜刀, 爆炸}；角色 {白名单内, 白名单外}；玩家数 {1, 2} |
| 边界值分析 | 平局容差 3 帧 → 测帧差 0 / 1 / 3 / 4；血量 1 点 / 0 点；出生点偏移 160 在房间边界处的表现 |
| 状态迁移 | IDLE→ARMING→COUNTDOWN→FIGHT→RESULT 的每条边，外加非正常回退（FIGHT 中 2P 退出 → IDLE） |
| 场景法 | 完整一局：加入 → 倒计时 → 对射 → 抢位 → 一方出局 → 结算 |
| 错误推测 | 炸弹炸门、传送道具、R 键重开、双方同帧归零、对局中断开手柄 |

**每条用例的必备字段**：用例号、关联需求、前置条件、步骤、预期结果、实际结果、证据、结论、执行人与日期。

**工具**：Markdown 表格起步；用例超过 100 条后再考虑禅道或 TestRail。

**产出**：`docs/testing/test-cases.md`

**完成标准**：任取一条用例交给没参与开发的人，他照着执行能得到与你一致的结论。

---

### P3 环境准备

**目标**：让每次执行都发生在完全相同的起点上。

**步骤**

1. 构建并同步：`npx isaacscript copy`，确认输出 `Mod compiled successfully` 与 `Mod copied successfully`。
2. 记录 `git rev-parse --short HEAD` 的值，这是本轮构建的唯一身份。
3. 备份或清空日志：把现有 `log.txt` 另存为 `log-<commit>-<日期>.txt`，避免新旧证据混在一起。
4. 核对存档槽与固定种子，写进报告的"环境"一节。
5. 准备两个手柄，确认连接方式（有线/无线）并记录。
6. 记录当前启用的 mod 列表（兼容性测试时逐个开关）。
7. 需要录屏时提前启动 OBS，确认分辨率与帧率设置。

**工具**：IsaacScript CLI、Git、VS Code、OBS。

**产出**：构建记录与环境记录（写入测试报告）。

**完成标准**：能在 3 分钟内把环境恢复到基线状态，且日志是干净的。

---

### P4 冒烟测试

**目标**：用最少时间回答"这个构建值不值得测"。

**步骤**

1. 启动游戏，确认日志出现模组初始化行与 `LOADED MOD` 行。
2. 开始一局 run，2P 在初始房间按 Start 加入。
3. 观察是否进入倒计时（日志出现 `阶段=COUNTDOWN`）。

**判定**：任何一步失败即为"不可测"，直接打回开发，**不进入 P5**。冒烟不通过时继续测功能，是纯粹的时间浪费。

**产出**：冒烟结论，写在测试报告最前面。

**完成标准**：明确写出"可测"或"不可测"及其证据。

---

### P5 功能测试

**目标**：逐条验证用例，产出可追溯的执行记录。

**步骤**

1. 按用例库顺序执行，不跳号、不合并。
2. 每条记录实际结果，并附证据（日志片段、截图或录像）。
3. 失败立即开缺陷单，分配 `BUG-M1-xx` 编号，并回填到用例的"关联缺陷"字段。
4. 若因环境或阻塞无法执行，标注"阻塞"并写明原因，不要标"通过"。

**纪律**

- 一次只改一个变量。
- 执行中发现的新问题，先记录，**不现场修**。
- "和预期不一样但好像也能用"——记录为失败，由评审决定是否放宽预期。

**工具**：游戏本体 + 手柄、日志、Snipaste（截图）、OBS（录像）。

**产出**：填充完毕的用例库 + 缺陷单。

**完成标准**：用例执行率 100%（含阻塞项），每条都有证据。

---

### P6 探索性测试

**目标**：找出用例库覆盖不到的破坏性场景。用例验证"设计的功能对不对"，探索验证"没人想到的用法会不会坏"。

**步骤**

1. 每次探索设定**时间盒**（如 20 分钟）和**一个主题**，不要漫无目的地玩。
2. 本项目的推荐主题：逃逸尝试（各种传送、开门、跨房间）；死亡与幽灵状态；与其余 mod 的相互干扰；手柄拔插与暂停。
3. 边玩边记录：时间点、操作、观察到的现象、怀疑的原因、能否复现。
4. 对每个确认可复现的问题开缺陷单；对每个"确实有风险但没坏"的场景，固化一条新用例。

**产出**：探索记录 + 新用例 + 缺陷单。

**完成标准**：每个主题至少产出一条新用例或一个结论，不允许"这次没发现什么"这种无信息量的收尾。

---

### P7 缺陷管理（贯穿全程，不是某个阶段）

**缺陷生命周期**

```
新建 → 评审（确认是否成立 + 定严重度）→ 修复中 → 待验证 → 验证通过 → 关闭
                                              ↘ 验证不通过 → 重开
                        ↘ 判定为非缺陷 → 关闭并写明理由
```

**严重度（影响多大）**

| 级别 | 定义 | 本项目例子 |
|---|---|---|
| S1 | 崩溃、无法启动、破坏存档 | 启用模组后游戏闪退 |
| S2 | 对局无法进行或无法结束 | 血量归零后不结算、房间锁不住导致无法继续 |
| S3 | 规则错误 | 友伤不生效、误伤自己、胜负判反、角色白名单失效 |
| S4 | 表现问题 | 倒计时位置偏移、文案错误、门移除后视觉突兀 |
| S5 | 平衡与建议 | 单次伤害过高、对局过短 |

**优先级（多快修）**：P1 立即（阻断测试）、P2 本轮内、P3 下轮、P4 有空再说。严重度高不等于优先级高——一个只在小众 mod 组合下出现的崩溃可以是 P3。

**缺陷单必备字段**：编号、标题、严重度、优先级、发现版本（commit hash）、环境、前置条件、复现步骤、期望结果、实际结果、复现率（每次 / 偶发）、证据（日志片段或录像）、关联用例。

**纪律**：一个缺陷单只写一个问题；修完之后既要验证该缺陷，也要回归它的关联用例。

---

### P8 回归测试

**目标**：保证"改好一个、没坏另一个"。

**触发时机**：每次代码提交、每次构建、每次发版前。

**回归集分级**

| 级别 | 内容 | 何时跑 |
|---|---|---|
| 自动化门禁 | `npm run lint` + `npx vitest run` + 日志断言脚本 | 每次提交 |
| 核心集 | M1 的主干用例（模式启用、锁房、互伤、结算、隔离） | 每次构建 |
| 全量集 | 全部用例 + 探索固化用例 | 发版前 |

**步骤**：确定本轮改动影响的模块 → 选择回归集 → 按用例执行 → 记录通过/失败 → 与上一轮结果对比，明确指出哪些能力退化。

**产出**：回归结果表（含与上轮的差异）。

**完成标准**：核心集 100% 通过，且没有新增 S1/S2 缺陷。

---

### P9 兼容性与稳定性测试

**兼容性矩阵**（每一行都要真实执行并记录，不允许推测）

| 维度 | 取值 |
|---|---|
| 游戏版本 | Repentance+ v1.9.7.17.J460（换版本需重测） |
| mod 组合 | 仅本模组 / 与已装的 30 个 mod 全开 / 与已知冲突 mod 单独开 |
| 手柄 | 两把手柄（有线/无线分别记录） |
| 显示模式 | 窗口 / 全屏；不同分辨率 |
| 角色 | 名单内角色（至少 4 个不同角色组合）/ 名单外被替换的角色 |

**稳定性测试**：连续打 10 局，记录崩溃次数、日志中的 error 行、帧生成时间抖动（OBS 或 RTSS 观测）。任何一次崩溃都要保留 `log.txt` 与 `crash_dumps\` 下的转储文件。

**产出**：矩阵结果表 + 稳定性记录 + 崩溃取证材料。

---

### P10 出报告与准出评审

**步骤**

1. 汇总：用例执行率、通过率、缺陷按严重度分布、遗留缺陷清单。
2. 写测试报告，环境一节照抄第 3 节的表格并填上本轮实际值。
3. 对照第 7 节的准出标准逐条判定，每条只能填"满足"或"不满足"，不满足必须写明影响与规避方案。
4. 签字（自己签也要签，并写明日期与 commit hash）。

**产出**：`docs/testing/test-reports/YYYY-MM-DD-<commit>.md`

**完成标准**：准出标准逐条有结论；报告能回答"这个构建能不能交给玩家用"。

## 6. 四份核心文档的模板字段

### 6.1 测试计划（test-plan.md）

测试范围（含明确的不测范围与理由）、准出标准、环境矩阵、轮次安排、资源与风险、角色职责。

### 6.2 用例库（test-cases.md）

| 字段 | 说明 |
|---|---|
| 用例号 | 如 `TC-M1-003`，与需求编号对应 |
| 关联需求 | `REQ-M1-02` |
| 前置条件 | 存档槽、种子、mod 组合、玩家数、角色 |
| 步骤 | 编号的可执行动作，写清"按哪个键、站哪个位置" |
| 预期结果 | 可观察的现象 + 应出现的日志 |
| 实际结果 | 执行时填写 |
| 证据 | 日志片段路径 / 截图文件名 / 录像时间点 |
| 结论 | 通过 / 失败 / 阻塞 |
| 关联缺陷 | `BUG-M1-xx` |

### 6.3 缺陷单（bugs.csv 或禅道）

6.2 之外见 P7 的字段清单。起步用 CSV 即可，字段为：编号、标题、严重度、优先级、发现版本、环境、前置条件、复现步骤、期望、实际、复现率、证据、关联用例、状态。

### 6.4 测试报告（test-reports/）

一句话结论、测试范围、环境、执行统计、缺陷统计与清单、遗留风险、与上一轮对比、准出判定、签字。

## 7. 准入与准出标准

**准入（满足才能开始测）**

1. `npm run lint` 与 `npx vitest run` 全部通过。
2. `npx isaacscript copy` 成功，且有明确的 commit hash。
3. 已知阻断问题已修复，冒烟测试可执行。
4. 本轮测试计划与用例库已就绪。

**准出（满足才能交付）**

1. 核心用例通过率 100%。
2. S1、S2 缺陷数量为 0。
3. S3 缺陷要么为 0，要么全部有书面规避方案并经确认。
4. 全部用例执行率 100%（阻塞项已记录原因）。
5. 兼容性矩阵必测行全部执行完毕。
6. 测试报告已产出并签字。

## 8. 可追溯性：把链条串起来

企业级测试与"随手试试"的分水岭是这条链是否闭合：

```
规格验收标准 (REQ)  →  测试用例 (TC)  →  执行结果  →  缺陷 (BUG)  →  复测结论
        ↑                                                              ↓
        └──────────────── 报告中的准出判定 ←──────────────────────────┘
```

维护方式：在 `traceability.md` 里建一张表，一行一个 REQ，列出它的用例、执行状态、关联缺陷。**任何一个 REQ 如果没有对应用例，就是覆盖漏洞；任何一个缺陷如果找不到关联 REQ，就要反问它是否属于本轮范围。**

## 10. 本项目的第一轮执行顺序

### 前置阻塞（必须先解决，否则测不了）

当前构建只要模组启用，**每一局 run 都会变成 PVP 对局**，而且门会被移除。这会让 `TC-M1-012`（非 PVP 场景与原版一致）根本无法执行——因为你无法构造"模组启用但不进入 PVP"的前置条件。

结论：**"PVP 模式开关"必须从 M4 提到测试开始之前**。这是一条独立的开发任务，照常走"规格 → 计划 → 实现 → 测试"。这也是测试反哺开发的典型案例：测试需求改变了功能优先级。

### 建议顺序

| 顺序 | 做什么 | 产出 |
|---|---|---|
| 1 | 实现 PVP 开关（开发任务） | 可通过开关控制是否进入对局 |
| 2 | 写 P0 测试计划 | `test-plan.md` |
| 3 | 写 P1 需求跟踪矩阵 | `traceability.md` |
| 4 | 写 P2 用例库（从规格第 8 节 + 本文档第 12 节的 12 条起步） | `test-cases.md` |
| 5 | 执行 P3 环境准备 + P4 冒烟 | 环境记录、冒烟结论 |
| 6 | 执行 P5 功能测试，逐条登记结果与缺陷 | 填充后的用例库、`bugs.csv` |
| 7 | P6 探索性测试（逃逸、死亡、mod 干扰三个主题） | 探索记录 + 新用例 |
| 8 | P8 回归 + P9 兼容性稳定性 | 回归表、矩阵表 |
| 9 | P10 出报告并对照准出标准判定 | `test-reports/` 下的报告 |

第一轮不必追求全量覆盖，先把 M1 的 12 条主干用例跑通、跑实，形成纪律和手感，再扩规模。

## 11. 常见坑（个人项目尤其容易犯）

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 用"感觉正常"代替证据 | 无法复现、无法回归 | 每条结论都附日志片段或截图 |
| 一次改多个地方再一起测 | 无法定位是哪个改动生效 | 一次只改一个变量 |
| 把偶发问题记为"偶尔会" | 无法评估影响 | 记录复现率（几次触发几次），并尝试找出触发条件 |
| 只测正常流程 | 上线后炸在最离谱的地方 | 每个功能配至少一条反面用例（逃逸、边界、异常中断） |
| 用例边测边改 | 前后结果不可比 | 用例版本冻结；修改要写明原因与时间 |
| 报告不写环境与 commit | 事后无法追溯是哪一版 | 环境一节照抄第 3 节表格并填实值 |
| 现象是"没反应"就直接怀疑功能 | 大概率是模组根本没加载 | **先查日志里有没有 `LOADED MOD` 与初始化行，再谈功能** |

最后这条已经有现成教材：本项目的第一次实机测试现象是"和原版一模一样"，日志只有两行——

```
[PVP] 开局 → 阶段=ARMING 房间=84
[PVP] 玩家数不足 → 阶段=IDLE 房间=84
```

它不是环境问题，是状态机把"等待 2P"误判成"玩家数不足"。如果没有日志，这次排查只能靠猜。**这就是为什么本流程把"日志断言"当成一等公民。**
